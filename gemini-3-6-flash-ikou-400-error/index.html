ホーム ／ Gemini 3.6 Flash

gemini-3.6-flash 移行後に HTTP 400 が出るとき：公式チェックリストに沿った項目別の修正

gemini-3-flash-preview や gemini-3.5-flash を gemini-3.6-flash に置き換えたあとリクエストが HTTP 400 になる場合は、まず二点を確認してください。リクエストの末尾が事前に埋めた model ターン（プレフィル）になっていないか、そして thinking_level と thinking_budget を同時に送っていないかです。Google 公式ページ「What's new in Gemini 3.6 Flash and 3.5 Flash-Lite」（https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.6、2026-10-13 更新）は、リクエスト内で最後の空でないターンが model ターンなら API は 400 エラーを返すと明記しています。同じページには、temperature、top_p、top_k は非推奨で無視されること、今後のモデル世代ではこれらを送ると HTTP 400 になることも書かれています。移行チェックリストでは candidate_count の削除、thinking_budget から thinking_level への置き換え、関数呼び出しコードの見直しも求められています。以下では Google のドキュメントに沿って各項目を確認し、最後に修正の確かめ方を説明します。

影響を受けるコード

非推奨モデルのページ（https://ai.google.dev/gemini-api/docs/deprecations、2026-10-22 更新）では、gemini-3-flash-preview と gemini-3.5-flash の後継として gemini-3.6-flash が挙げられています。gemini-3.5-flash については、エンドポイントは停止せず API リクエストを自動的に gemini-3.6-flash にルーティングすること、Google AI Studio ではこのモデルを選択できないことが追記されています。

つまり Google の API を直接呼び出していて、コードがまだ gemini-3.5-flash を指定している場合でも、リクエストはすでに gemini-3.6-flash が処理しています。このページで扱うルールはそのようなコードにも当てはまります。

新機能ページでは現在、gemini-3.6-flash と gemini-3.5-flash-lite を Gemini 3 シリーズの前世代リリースで本番利用は引き続き可能と位置付け、最新の Flash モデルとして Gemini 3.8 Flash を案内しています。非推奨モデルのページでは gemini-3.6-flash の停止日は発表されていません。公式ガイドは、Gemini 3.5 Flash、Gemini 3 Flash（Preview）、Gemini 3.1 Pro から 3.6 Flash への移行を対象にしています。

Google によると、これらの API 変更は Gemini 3.6 Flash と Gemini 3.5 Flash-Lite、そして今後リリースされるすべての Gemini モデルに適用されます。そのため、ここで行う修正はより新しいモデルに移るときにも残しておくのが無難です。

model ターンのプレフィルが 400 になる

公式ガイドによると、model ターンのプレフィルはサポートされなくなりました。リクエスト内で最後の空でないターンのロールが model の場合、API は 400 エラーを返します。プレフィルとは、contents の末尾に model ロールのターン（たとえば JSON オブジェクトの書き出し部分）を置き、モデルにその続きから書かせる手法です。

このルールが対象にするのは最後の空でないターンだけです。user と model のターンが交互に並ぶ通常の会話履歴は、最後の空でないターンが model でなければ問題ありません。

Google は代わりの方法を二つ示しています。書式やトーンの要件を system_instruction に記述する方法と、Structured outputs（https://ai.google.dev/gemini-api/docs/structured-output）で応答の形式を制約する方法です。JSON を得るためにプレフィルを使っていた場合は、Structured outputs に切り替えられます。

切り分けるには、実際に API へ送られているリクエスト本文をログに出し、contents の最後の空でないターンが model になっていないかを確認します。中間ライブラリを使っている場合は、自分のコードだけでなく、そのライブラリが送っている本文を確認してください。

temperature、top_p、top_k と candidate_count

移行ガイドによると、temperature、top_p、top_k は非推奨で API に無視されます。今後のモデル世代ではこれらのパラメータを送ると HTTP 400 が返るため、すべてのリクエストから削除するよう求められています。3.6 Flash では現時点でエラーにはなりませんが、効果もありません。

実務上の影響として、応答を安定させるために temperature を 0 にしていたコードは、3.6 Flash ではその効果を得られません。決定性を高めたい場合、Google はユースケースに合わせた明確なルールを書いた system instruction を定義するよう勧めています。

チェックリストでは candidate_count の削除も求められています。Google によると candidate_count は Gemini 3 以降でサポートされていません。

参考までに、Gemini 3 の開発者ガイド（https://ai.google.dev/gemini-api/docs/gemini-3）は現在「非推奨で削除予定」と表示されていますが、temperature はデフォルト値 1.0 のままにすることを強く推奨し、1.0 未満にするとループや性能低下などの予期しない動作につながる可能性があると注意していました。3.6 Flash の移行ガイドはそれより新しい指示で、これらのパラメータは単に削除する、という扱いです。

thinking_budget を thinking_level に置き換える

チェックリストでは thinking_budget を thinking_level に置き換えるよう求めており、値として medium または high が示されています。公式の Thinking ページ（https://ai.google.dev/gemini-api/docs/thinking）の表では、gemini-3.6-flash の思考はデフォルトで有効（medium）で、minimal、low、medium、high の各レベルに対応しています。この表にはこのモデルで思考をオフにする選択肢は載っておらず、最も低いレベルは minimal です。

gemini-3-flash-preview から移る場合はデフォルト値に注意してください。同じ表で gemini-3-flash-preview のデフォルトは high、gemini-3.6-flash のデフォルトは medium です。コードで思考レベルを指定せずデフォルトに任せていた場合、切り替え後は実際のレベルが high から medium に下がります。以前の挙動を保ちたいなら high を明示してください。gemini-3.5-flash から移る場合はデフォルトは変わりません。Google は、3.6 Flash は 3.5 Flash と同じ medium をデフォルトの思考レベルとして使うと説明しています。

非推奨となった Gemini 3 ガイドには、thinking_budget は後方互換のため引き続きサポートされるものの、thinking_level と旧来の thinking_budget を同じリクエストで使うことはできず、そうすると 400 エラーが返ると書かれています。新しいフィールドを追加したら、両方を送るのではなく古いほうを削除してください。

Google のサンプルは Interactions API を使っており、思考レベルは generation_config 内の thinking_level フィールドで指定しています。generateContent では思考関連フィールドの名前や位置が異なる場合があるため、Interactions API のサンプルのフィールド名をそのまま流用せず、API リファレンス（https://ai.google.dev/api/generate-content）の GenerationConfig を確認してください。

関数呼び出しと thought signature で確認すること

チェックリストでは関数呼び出しのコードを見直すよう求めています。一つ目は、マルチモーダルなアセットをレスポンスのペイロード（response payload）の中に置くことです。Function calling のページ（https://ai.google.dev/gemini-api/docs/function-calling）によると、Gemini 3 シリーズのモデルでは function_result ステップの result フィールドに一つ以上のコンテンツブロックを入れて送ることができ、各ブロックには text や image などの type を指定する必要があります。

二つ目は、インラインの指示を二つの改行（\n\n）で区切って書式を整えることです。公式チェックリストにはこれ以上の説明はありません。

三つ目は Malformed_Function_Call です。Function calling のページによると、ツール呼び出しの直前に構造化テキスト（XML、YAML、JSON など）を出力するようプロンプトで求めると、そのツール呼び出しがときどき Malformed_Function_Call で失敗することがあります。推奨される対処は、ツール呼び出し前のメモを生のテキストではなく専用の update 関数の呼び出しに入れるようモデルに指示することです。update 関数は previous_step、plan、next_step、external の四つの STRING 型パラメータを持ち、四つとも必須として宣言します。代わりの方法として、メモを Markdown の見出し（# UPDATE、## PLAN など）として書かせる、またはツール呼び出しの前にテキスト出力を求めない、という二つが挙げられています。

thought signature について、Function calling のページは SDK が自動で処理すると説明しています。会話履歴を自分で管理する場合（ステートレスモード）は、Thinking ページによると、すべての thought ブロックを受け取ったとおりに再送する必要があり、履歴から削除したり変更したりしてはいけません。セッションの途中でモデルを切り替える場合も同様です。ステートフルモード（store を true にし、以降のターンで previous_interaction_id を渡す）では、signature について何もする必要はありません。API リファレンスには終了理由 MISSING_THOUGHT_SIGNATURE もあり、「リクエストに thought signature が少なくとも一つ欠けている」と説明されています。これが出た場合は、履歴から thought ブロックが失われていないか確認してください。

エラーメッセージの出ない挙動の変化

移行ガイドによると、3.6 Flash は Gemini 3.5 Flash よりも、変更を加える前に診断用のスクリプトを実行することを好む頻度が高くなっています。Google は、これにより複雑なタスクでの精度が上がる一方、定型的なフロントエンド作業では探索的なステップが増えることがあると説明しています。

また、ビジュアルのレイアウトやスタイルについては、人間の評価者が以前のモデルを好んだとされています。Google は、明確なデザインガイドラインを与えることでこれを緩和できるとしています。

Google はさらに、3.6 Flash は Gemini 3.5 よりも少ない推論ステップ、会話ターン、ツール呼び出しで複数ステップのワークフローを完了すると述べています。これで利用量が変わるかどうかは、ご自身の請求データで確認してください。料金は OpenLux の料金ページで確認してください。

修正できたかの確認方法

手順 1：/v1/models エンドポイントを呼び出し、一覧に gemini-3.6-flash があることを確認します。そのうえで、アプリケーションのコードが実際に新しいモデル名を使っていることを確認します。

手順 2：最後の空でないターンが user で、temperature、top_p、top_k、candidate_count を含まず、思考パラメータは一つだけ（thinking_level）の最小リクエストを送ります。ステータス 200 で本文付きの応答が返り、以前の 400 エラーが出なくなったことを確認します。

手順 3：思考レベルが実際に効いているかを確認します。generateContent の応答では usageMetadata.thoughtsTokenCount フィールドが思考トークン数を示します（Interactions API では total_thought_tokens で返ります）。同じプロンプトを low と high で一回ずつ送り、値を比べて設定がモデルに届いていることを確認します。

手順 4：プレフィルを Structured outputs に置き換えた場合は、実際の入力例をいくつか試し、応答が期待どおりにパースできることを確認します。関数呼び出しを使う場合は、複数のツール呼び出しを含む一連のフローを最後まで実行し、Malformed_Function_Call と MISSING_THOUGHT_SIGNATURE のどちらも出ないことを確認します。

非推奨モデルのページにある gemini-3.5-flash から gemini-3.6-flash への自動ルーティングは、Google 自身の API の挙動です。中継経由で gemini-3.5-flash を指定したときにどのバージョンが応答するかは、このページでは確認していません。移行の際はモデル名を直接 gemini-3.6-flash に変え、上記のチェックリストを適用して挙動を明示的にしてください。
